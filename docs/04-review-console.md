# ④ 轻量级校对台（Review Console）

> 在真正生成 Word 前，把解析结果列成**树状大纲**（只显示被识别为标题、摘要、图表的行）。
> 你花 30 秒扫一眼，发现某句正文被误认成「二级标题」，鼠标点一下改成「正文」。
> 这一步把「自动化效率」和「人工兜底」结合得最丝滑。

---

## 1. 目标与非目标

**目标**
- 30 秒内完成一次人工纠偏。
- 只暴露「可能有问题的块」和「骨架结构」，不淹没在全文里。
- 纠偏结果可持久化、可重放（同一份修正重跑不再问）。

**非目标**
- 不做全文逐段校对（那是另一件事）。
- 不做富文本编辑（只改标签，不改内容）。

---

## 2. 树状大纲的数据源

校对台消费的是解析后的 `list[Block]`，但只展示**结构相关的块**：

- 所有 `heading_*`（按层级缩进成树）
- `abstract_title` / `abstract_body` / `keywords`
- `caption`（挂在最近的 `image`/`table` 前）
- `reference_title`（折叠显示，不逐条展开）
- 被标记为「疑似」（`confidence < 阈值` 或 `need_llm` 命中）的块——**重点高亮**

其余 `body` 块默认折叠为「正文 N 段」，可展开查看但不强制。

---

## 3. 交互设计

### 3.1 视图布局

```
┌─────────────────────────────────────────────────────┐
│ 论文：毕业论文_v3.docx   规则：本科规范 v1   [渲染]  │
├─────────────────────────────────────────────────────┤
│ 大纲（点击行可改标签）                     [仅看疑似] │
│  ▼ 第一章 绪论                     [heading_1 ▾]     │
│  ▼ 1.1 研究背景                   [heading_2 ▾]     │
│     • 图 1-1 系统架构              [caption ▾]       │
│     • [疑似标题] 本文提出了一种…   [body ▾] ⚠ 低置信 │
│  ▼ 1.2 研究意义                   [heading_2 ▾]     │
│  ▶ 第二章 相关工作 (折叠)          [heading_1 ▾]     │
│  ▶ 参考文献 (6 条)                 [reference_title] │
└─────────────────────────────────────────────────────┘
```

### 3.2 单个块的编辑
- 点击行的「标签下拉」→ 选择正确 `BlockType`。
- 支持键盘：↑↓ 移动、Enter 确认、数字键快速选常见标签。
- 修改后 `source = "human"`，记入修正日志。

### 3.3 批量操作（可选）
- 「把选中若干块设为正文」
- 「全部置信度 > 0.95 的自动接受」

## 4. 技术形态选择

| 形态 | 优点 | 缺点 | 建议 |
|------|------|------|------|
| **本地 Web（推荐）** | 直观、可复用前端、远程可用 | 需起服务 | ✅ 默认 |
| CLI 树（textual/rich） | 无依赖、SSH 友好 | 交互弱 | 备选 |
| 直接改 JSON | 最简单 | 易错、不直观 | 仅调试 |

推荐：**本地轻量 Web**——后端 FastAPI/Flask 提供 `GET /review` 返回大纲 JSON，前端用任意轻量框架渲染树；提交 `POST /review/apply` 回写修正。

---

## 5. 修正结果的持久化与重放

- 修正文件：`review_fixes.json`（与任务绑定）：

```jsonc
{
  "doc_id": "毕业论文_v3",
  "fixes": [
    { "block_id": "b0032", "from": "heading_2", "to": "body", "by": "human", "at": "2026-11-24T12:00:00+08:00" }
  ]
}
```

- **重放**：同一 `doc_id` 再次运行时，渲染前自动套用 `review_fixes.json`（按 `block_id` 覆盖解析结果），避免重复人工。`block_id` 在 Ingestion 阶段稳定生成（基于文档流序号 + 内容哈希），保证跨运行可对齐。

> `block_id` 稳定性是重放的关键。见 §06 的 ID 生成约定。

---

## 6. 与渲染的衔接

- 校对台只改「标签」，不触碰内容与资产。
- 应用修正后，渲染层以「最终标签」为准套样式。
- 若用户在校对台标记某块「需人工核对公式」，则渲染层在该块处保留原样并在质检日志中提示。

---

## 7. 接口契约（详见 §06）

```python
class ReviewConsole(Protocol):
    def build_outline(self, blocks: list[Block]) -> OutlineNode: ...
    def apply_fixes(self, blocks: list[Block], fixes: list[Fix]) -> list[Block]: ...
    def load_fixes(self, doc_id: str) -> list[Fix]: ...
    def save_fixes(self, doc_id: str, fixes: list[Fix]) -> None: ...
```

Web 形态额外提供 HTTP 层：
- `GET  /api/review/{doc_id}` → 大纲 JSON
- `POST /api/review/{doc_id}/fixes` → 提交修正
- `POST /api/review/{doc_id}/render` → 触发渲染

---

## 8. 可用性细节

- **疑似块高亮**：低置信（< 0.9）、LLM 命中、启发式标题，均高亮。
- **进度记忆**：可「接受当前全部建议并继续」。
- **撤销**：支持单步撤销上一次标签修改。
- **快捷键说明**：首次进入显示 3 秒提示。
